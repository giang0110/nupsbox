# NupsBox Phase 2 P2.3 — CRM Enhancement Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the Phase 1 lead list into a practical internal CRM with deterministic pipeline transitions, lead detail, assignment, append-only notes, server-side search/filter/pagination, and admin-only audited CSV export.

**Architecture:** Build on P2.1’s permission/status/RLS/audit contracts. All business mutations use the authenticated Supabase server client and remain RLS-bound; database triggers own status history and mutation audit. Read models are server-side, page size is fixed at 50, and CSV export is a server route with a narrow database audit RPC rather than client-side table extraction.

**Tech Stack:** Next.js 16.3.3 App Router/Server Actions/Route Handlers, React 19.3, TypeScript 5.9, Zod 4.6, Supabase/PostgreSQL/RLS, Vitest 5, pgTAP.

**Spec:** `docs/superpowers/specs/2026-09-14-phase2-conversion-operations-design.md`

## Global Constraints

- P2.1 and P2.2 must be green before P2.3.
- Page size is exactly 50; pagination and filtering are server-side.
- Operational statuses: `new → contacted → qualified → viewing → negotiating → won`; `lost` from any non-terminal state.
- Staff may move forward one approved pipeline step or mark lost. Admin may do the same plus backward correction and terminal reopen; admin does not skip forward stages.
- Every status/assignment/note mutation is audited through P2.1 database triggers.
- Notes are append-only in Phase 2.
- Assignment target must be an active `admin` or `staff` profile.
- Only admin has `leads:export`.
- CSV export audit contains actor/filter scope/count only; it never copies exported PII into `audit_log`.
- No external CRM, email automation, SMS or Zalo automation is introduced.

- [ ] **Step 3: Implement explicit transition tables**

Use a data structure, not loose ordinal mutation:

```ts
const nonTerminalOrder: readonly OperationalLeadStatus[] = [
  'new', 'contacted', 'qualified', 'viewing', 'negotiating'
];

const staffTransitions: Record<OperationalLeadStatus, readonly OperationalLeadStatus[]> = {
  new: ['contacted', 'lost'],
  contacted: ['qualified', 'lost'],
  qualified: ['viewing', 'lost'],
  viewing: ['negotiating', 'lost'],
  negotiating: ['won', 'lost'],
  won: [],
  lost: []
};
```

Transition rules:

```text
staff → only `staffTransitions[from]`
admin → any staff transition
admin → backward correction when from/to are non-terminal and target is earlier in nonTerminalOrder
admin → reopen from won/lost to any non-terminal status
admin → no direct won↔lost transition
admin → no forward skip such as new→negotiating
viewer → none
```

All roles still require the shared `leads:update` permission before transition logic is evaluated.
